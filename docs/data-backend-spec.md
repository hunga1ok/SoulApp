# Data and backend specification

## 1. Backend boundary

`SoulApi` is the only application allowed to access PostgreSQL and object-storage credentials. Flutter and the admin web app communicate with it through versioned HTTPS REST endpoints.

The backend is a modular NestJS application, not a collection of client-side database calls. Its modules should initially cover:

- `auth` and application sessions;
- `profiles` and user preferences;
- `content` and localization;
- `visions` and private images;
- `journey`, responses, and journal entries;
- `audio` and category playlists;
- `admin` import, review, and publishing.

## 2. Authoring sources

- `Soul_28_Day_Journey_Content_Dataset_v1.1.xlsx`
- `Soul_Vision_Board_Content_Dataset_v1.2.xlsx`
- `Soul_External_Content_Library_v1.0.xlsx`
- `Soul_Owned_Content_Pack_v1.0.docx`
- `audio-manifest.json`

These are import sources, not runtime assets. A deterministic import command validates and normalizes them into PostgreSQL records.

## 3. Content entities

The normalized model must cover:

- Vision categories.
- Feelings and category-feeling membership.
- Guided Vision questions and suggested answers.
- Statement templates and affirmations.
- Owned/licensed audio assets and category-audio mappings.
- Vision Session definitions.
- 28 journey days, tasks, notifications, affirmations, and content mappings.
- External curated content and editorial/license status.
- Locale-specific text using explicit `vi`, `en`, or `neutral` metadata.

Static content records require stable source IDs so repeated imports update rather than duplicate them.

## 4. User entities

### Profile

- Application user ID generated by the backend.
- Google subject ID stored as an identity link, not used as display name.
- Preferred display name, independent of Google metadata.
- Locale: `vi` or `en`.
- Audio-enabled preference.
- Reminder preferences and onboarding completion.

### Vision

- Owner, category, statement, image object key, timestamps, archived state.
- One to three selected feeling codes.
- Resolved category playlist or a stable mapping-version reference.

### Journal

- Owner, type, body, occurrence date, timestamps.

### Journey

- Owner, journey code, day number, status, completion timestamp.
- Task responses stored as typed JSON payloads validated by the task schema.

## 5. Authentication and authorization

1. Flutter signs in with Google and sends the resulting identity proof to `POST /v1/auth/google`.
2. The API verifies issuer, audience, signature, expiry, and Google subject.
3. The API creates or links the Soul user and issues a short-lived access token plus rotating refresh token.
4. Refresh-token values are hashed in PostgreSQL and may be revoked per device/session.
5. Every private query includes the authenticated application user ID; client-supplied ownership fields are ignored.

Admin users authenticate through the same backend but require an explicit `admin` or `editor` role. Admin browser sessions use secure, HTTP-only cookies. The API, not the page UI, enforces every role and publication permission.

## 6. Audio contract

Required audio metadata:

- Stable ID and title.
- Vision Category or journey usage.
- Locale: `vi`, `en`, or `neutral`.
- Format: spoken, instrumental, ambient, or nature.
- Ownership: Soul-owned or licensed.
- License proof reference and review status.
- Object key, duration, checksum, and publication status.

Playback eligibility:

- `neutral` audio may play in either locale.
- `vi` spoken audio is eligible only for Vietnamese.
- `en` spoken audio is eligible only for English.
- Unverified or unpublished files are never returned by playback endpoints.
- YouTube and Spotify records are external discovery content only.
- Vision playlists are resolved from the Vision Category, not selected feelings and not manual user selection.

## 7. Object storage

- `vision-images/{user_id}/{vision_id}/{file}`: private; API-authorized upload/read/delete only.
- `audio/{locale_or_neutral}/{audio_id}/{file}`: published owned/licensed audio; administrative write access only.
- Prefer short-lived pre-signed upload/download URLs after API authorization.
- Store only object keys and metadata in PostgreSQL; do not store binary image/audio blobs in tables.
- Validate content type, maximum size, checksum, and image dimensions before finalizing uploads.

The provider may be AWS S3, Cloudflare R2, or self-hosted MinIO. Application code targets the S3-compatible interface so the provider remains replaceable.

## 8. API conventions

- Prefix endpoints with `/v1` and publish an OpenAPI document.
- Use consistent error envelopes with machine-readable codes and localized UI mapping in Flutter.
- Use cursor pagination for growing lists.
- Make create/update operations idempotent where retries are expected.
- Apply database transactions to multi-record state changes and imports.
- Add rate limits to authentication, upload authorization, and sensitive writes.
- Never log tokens, private journal text, signed URLs, or full Google payloads.

## 9. Configuration contract

Flutter receives only public application configuration:

```text
API_BASE_URL
GOOGLE_WEB_CLIENT_ID
OAUTH_REDIRECT_SCHEME
```

Backend configuration is supplied by its deployment environment:

```text
DATABASE_URL
JWT_PRIVATE_KEY / JWT_PUBLIC_KEY
GOOGLE_CLIENT_IDS
OBJECT_STORAGE_ENDPOINT
OBJECT_STORAGE_BUCKET
OBJECT_STORAGE_ACCESS_KEY
OBJECT_STORAGE_SECRET_KEY
```

Commit example values only. Production, staging, and development use separate databases, storage buckets, keys, and OAuth configuration.

## 10. Import verification

An import is accepted when:

- Source IDs are unique and stable.
- Re-running the import creates no duplicates.
- All expected Vision Categories and expanded feelings are present.
- All 28 journey days and their tasks are present.
- Every native audio mapping references a reviewed published asset or remains explicitly unavailable.
- Locale and editorial filters exclude mismatched or unverified content.
- The import can run in dry-run mode and reports row-level errors before any write.
